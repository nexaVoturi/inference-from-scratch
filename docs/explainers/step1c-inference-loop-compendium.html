01 / The trusted baseline

Block 1: Make a reference answer

Why I need this blockThe reference must be independent of my hand-written code. If my implementation is wrong, I need a reliable comparison point.

step1a_load.py loads the pinned Qwen3-0.6B snapshot through Transformers. It applies the chat template. It performs greedy generation for 32 tokens. It writes the prompt IDs and generated IDs to engine/out/reference.json.

model = AutoModelForCausalLM.from_pretrained(snapshot_dir(), dtype=torch.bfloat16).to(dev).eval()

gen = out[0, ids.shape[1]:].tolist()

These IDs do not calibrate my Mac. They form a golden reference. My later code runs on the same machine, but it must match this recorded behavior.

Key takeaway: The reference tells me what should happen. It does not tell me how the model produced the answer.

02 / The first pass

Block 2: Prefill the prompt

Why I need this blockBefore generating the next token, the model must process the whole prompt. I call this first pass prefill.

The prompt contains 20 token IDs. An embedding lookup turns them into a matrix with one row per token and 1,024 features per row. The matrix then passes through all 28 transformer layers.

At the end of prefill, the model has one score for every vocabulary token at the final position. Greedy decoding selects the token with the largest score. In my example, the response starts with “The three largest cities…”

Key takeaway: Prefill reads the prompt. It gives me the first next-token decision and the key/value history for decode.

Source: step1c_autoregressive.py, lines 179–193 and 195–211; model dimensions: config-walkthrough.md.

03 / One transformer block

Block 3: Compute one layer’s update

Why I need this blockOne layer is the unit I must understand before reasoning about the whole model. It has two jobs. It lets positions exchange information through attention. It then transforms each position through the MLP.

residual = hidden
normed = rmsnorm(hidden, input_layernorm, eps)
q = normed @ q_proj.T; k = normed @ k_proj.T; v = normed @ v_proj.T
# reshape heads, normalize Q/K, apply RoPE, attend, project back
hidden = residual + attn_out
residual2 = hidden
# post-attention norm, gated MLP, then the second residual
hidden = residual2 + mlp_out
Key takeaway: I use attention to mix positions, then use the MLP to transform each position. Finally, residual additions carry the current stream forward.

04 / After the first token

Block 4: Decode one token at a time with a KV cache

Why I need this blockText generation is sequential. Token 2 depends on token 1. Token 1 depends on the prompt. Future tokens cannot be generated in parallel. The cache prevents repeated work on old key and value vectors.

After prefill, the loop chooses the first generated token. At the next step, only that new token enters the 28 layers. Each layer reads its old K/V tensors, appends the new K/V pair, and attends over the full prefix.

if cache is not None:
    old_k, old_v = cache
    k = torch.cat((old_k, k), dim=1)
    v = torch.cat((old_v, v), dim=1)
new_cache = (k, v)

In my educational implementation, torch.cat makes the growing contiguous cache visible. A production engine normally uses paged or preallocated storage. That layout avoids repeated copies of the whole history.

Key takeaway: Prefill creates the initial history. Decode adds one position at a time. The KV cache connects those two phases.

Source: step1c_autoregressive.py, lines 132–140 and 195–211.

05 / The memory bill

Block 5: Turn the cache shape into bytes

Why I need this blockContext length is a memory value, not only a model setting. Every extra token adds K/V state in every layer. I calculate the memory slope before I choose a serving configuration.

For batch size 1, the cache stores 28 layers, 8 KV heads, 128 values per head, and both K and V in BF16. The cache cost grows in direct proportion to sequence length.

bytes = batch × layers × 2(K,V) × KV_heads × head_dim × sequence × bytes_per_value

06 / Trying a different attention path

Block 6: Full attention versus tiled attention

Why I need this blockThe full path creates the complete score and probability matrices. The tiled path processes smaller pieces and keeps a running softmax. I test the tiled path to reduce temporary memory and memory movement. Less memory does not always mean more speed.
for start in range(0, kv_len, block_size):
    scores = q @ k[:, start:stop].T
    # mask future positions, then update online softmax state
    running_sum = running_sum * old_scale + exp_scores.sum(-1, keepdim=True)
    running_out = running_out * old_scale + exp_scores @ v[:, start:stop]

The running maximum keeps exponentials numerically stable. The running sum is the softmax denominator. The running output is the numerator. At the end, the numerator is divided by the denominator.

Important result: On my CPU, the tiled path was slower. It took 24.7 ms per decode token. The full path took 22.6 ms. The Python loop added more time than the memory-saving idea removed. This result does not support a claim that tiling is always faster.
Key takeaway: Every optimization needs two tests. Does it preserve the output? Does it improve the target hardware and workload? Passing the first test does not pass the second.

Source: step1c_autoregressive.py, lines 47–89 and 141–163; timing harness: step1e_profile.py.

Practice / Apply the mechanism

Check yourself

  1. Why do I save the Hugging Face output before I write the manual loop?
  2. What is the difference between prefill and decode?
  3. Why does the KV cache grow during generation?
  4. Which part of the transformer block mixes token positions? Which part works independently per position?
  5. Why can tiled attention be correct but slower?
  6. What does a 32/32 token match prove? What does it not prove?

Answers

  1. I create an independent behavioral reference. A wrong answer says that I calibrate the Mac. That confuses a correctness fixture with hardware calibration.
  2. Prefill processes the whole prompt. Decode processes one new token at a time. Treating them as one workload hides the different shapes and costs.
  3. Each new position adds one key and one value to every transformer layer. The cache preserves prior context, so the model does not recompute it.
  4. Attention mixes positions. The MLP transforms each position independently. Calling the MLP a cross-token mixer confuses it with attention.
  5. The implementation and the hardware matter. Tiling can reduce temporary matrices, but a Python loop can add enough overhead to lose on CPU.
  6. It proves that the observed generated IDs match the reference for this case. It does not prove speed, production readiness, generalization to every prompt, or transfer from CPU or MPS to CUDA.
