01 / The starting representation

One row for each token

Reader questionHow does each token ID become a row in the hidden-state matrix?

Correct. Each token ID selects one row from this language model’s learned embedding table. With 20 tokens and a hidden size of 1,024, hidden has shape [20, 1024]. These are the model’s own embeddings, not the output of a separate embedding model.

hidden = F.embedding(prompt_ids, w["model.embed_tokens.weight"])

At this point, two occurrences of the same token ID receive identical vectors. Attention can later make them different because their positions and available context differ. The matrix keeps its row-per-token structure as the representations change.

02 / Residual connections

What does “a direct path forward” mean?

Reader questionHow does a residual connection carry the existing representation forward?

The incoming representation takes two paths. One goes through normalization and attention to calculate an update. The other carries the input unchanged to an addition. The addition combines them.

residual = hidden
normed = rmsnorm(hidden, w[p + "input_layernorm.weight"])
# ... attention computes attn_out from normed ...
hidden = residual + attn_out

Keeping information from the input does not require the attention branch to reproduce it in its own output. The input is already supplied to the addition. If the update is zero, the output equals the input.

Illustrative arithmetic — invented values, not a model trace
QuantityFour-feature vector
Incoming representation[2.0, -1.0, 0.5, 3.0]
Attention update[0.0, +0.2, -0.1, 0.0]
Sum passed onward[2.0, -0.8, 0.4, 3.0]

A path is not a guarantee of preservation. An update can reinforce, change, or cancel a feature: 2 + (-2) = 0. And the next sublayer receives the sum, not separate records of the old vector and its update.

During training, the addition also provides a direct gradient term: for y = x + F(x), the derivative includes the identity alongside the derivative through F. This helps explain why the path is useful for learning, although this script only runs inference.

03 / Following the representation

What does layer 2 receive?

Reader questionDoes each layer receive the original embedding, or the output from the previous layer?

Every layer receives the previous layer’s output. “Original input” at a residual connection means the input to that particular sublayer. It does not always mean the initial token embedding.

Layer 2 reads x₂, which already includes the effects of layers 0 and 1. It does not receive a separate, untouched copy of x₀. It also cannot generally recover the earlier updates individually from their sum.

There are two residual additions inside each layer

Your summary was close: a layer adds an attention update and an MLP update. The crucial detail is that these happen sequentially. The MLP reads the result of the attention addition.

a = Attention(Norm₁(x))
y = x + a
m = MLP(Norm₂(y))
z = y + m

Here, a and m are updates. The complete layer output is z, including its residual input. Normalization happens before attention and before the MLP; we are not normalizing their outputs before adding them.

hidden = residual + attn_out
residual2 = hidden
normed2 = rmsnorm(hidden, w[p + "post_attention_layernorm.weight"])
gate = normed2 @ w[p + "mlp.gate_proj.weight"].T
up = normed2 @ w[p + "mlp.up_proj.weight"].T
mlp_out = (F.silu(gate) * up) @ w[p + "mlp.down_proj.weight"].T
hidden = residual2 + mlp_out

Two kinds of processing: attention combines information across permitted token positions. The MLP transforms each position independently, using the same layer weights at every position. Both return updates with the residual stream’s width of 1,024.

04 / Controlling scale

RMSNorm operates on each row

Before attention, RMSNorm measures the scale of each token’s vector, divides by that scale, and applies learned feature weights.

rᵢ = √(mean(xᵢ²) + ε)
norm(xᵢ) = weight ⊙ (xᵢ / rᵢ)

The mean is over the features in one row. The symbol ⊙ means elementwise multiplication. Epsilon is a small positive value that keeps the denominator away from zero.

As an illustrative calculation, ignoring epsilon and setting the weights to 1: [3, 4] has RMS √12.5 ≈ 3.536, giving approximately [0.849, 1.131]. The vector [30, 40] gives the same result under those assumptions. A nonzero epsilon makes scale invariance approximate.

Dividing by a single positive scalar preserves a row’s relative proportions. The learned feature weights can then change those proportions. RMSNorm does not subtract the mean, force values into a fixed range, or make the vector’s Euclidean length equal to 1.

dtype = x.dtype
x32 = x.float()
x32 = x32 * torch.rsqrt(x32.pow(2).mean(-1, keepdim=True) + eps)
return weight * x32.to(dtype)

mean(-1, keepdim=True) reduces the feature axis while retaining a singleton dimension for broadcasting. rsqrt computes the reciprocal square root. This implementation normalizes in FP32, casts back, then multiplies by the learned weights.

Connect it to the residual path: attention receives the normalized representation. The skip branch still carries the unnormalized input to the addition.

Code: lines 30–36 and 66–67. Later Q/K norms operate per head; the “20 scales” explanation here applies specifically to the input matrix of shape [20, 1024].

05 / Query, key, and value projections

If Q, K, and V come from the token, why are they different?

Reader questionHow do separate Q, K, and V projections assign different roles to the same hidden representation?

They originate from the same representation, but each is transformed by a different learned matrix. Each output feature is a weighted combination of input features. Different matrices produce different combinations.

q = normed @ w[p + "self_attn.q_proj.weight"].T
k = normed @ w[p + "self_attn.k_proj.weight"].T
v = normed @ w[p + "self_attn.v_proj.weight"].T

Query

Intuition: what this position is looking for.
Literal role: a vector used to score keys.

Key

Intuition: what this position can be matched on.
Literal role: a vector scored by queries.

Value

Intuition: what this position contributes.
Literal role: a vector included in a weighted sum.

The operations give the vectors their roles

Within one head, the query at position i is compared with keys at allowed positions j. Scaled dot products become scores. A causal mask excludes future positions, and softmax turns the remaining scores into attention weights that sum to 1.

score[i, j] = dot(q[i], k[j]) / √head_dim
weights[i, :] = softmax(masked scores[i, :])
head_output[i] = Σⱼ weights[i, j] × v[j]

The sum is where information is mixed between positions. Queries and keys determine the weights; values provide what gets combined. The head outputs are concatenated and projected back to width 1,024 before the residual addition.

Illustrative arithmetic Suppose a query is [2, 0]. Key A is [3, 0] and key B is [0, 3]. Their raw dot products are 6 and 0. If both positions are allowed, A receives more weight after scaling and softmax. A’s value therefore contributes more strongly; its key is not the content being averaged.

Why separate keys from values? Features useful for matching can differ from features useful for passing onward. Separate learned projections allow the model to make that distinction.

Why is Q wider than K and V here?

This configuration uses 16 query heads and 8 key/value heads, each 128 features wide. Hence Q has width 2,048 and K/V each have width 1,024. The code splits the projections into heads, applies Q/K normalization and positional rotation, then shares each KV head across two query heads. Dot products occur between matching 128-feature vectors, not between the unsplit 2,048- and 1,024-feature rows.

Sections 7–9 unpack the projection widths and head reshaping. The next sections follow those head-shaped tensors through normalization, position encoding, KV sharing, masking, and the final weighted sum.

Code: projection lines 69–71; head preparation lines 73–85; scores, mask, weighted values, and output projection lines 87–92.

06 / How these roles become useful

The computation assigns the role. Training learns the numbers.

Reader questionHow do the learned projection matrices acquire these roles?

There is no instruction stored in a query saying “find a noun” or “look for position A.” During training, prediction errors produce gradients through the model, including its attention computations. Updates to the projection matrices can make the resulting queries, keys, and values more useful for predicting tokens.

During inference, the matrices stay fixed. The activations change with the input and context. Later layers use their own learned matrices and operate on representations already revised by earlier layers.

The “looking for” analogy describes an effect of learned numerical matching. It does not imply that each head or feature has a single, human-readable meaning.

Reconnect the complete picture

  1. Embedding: create one vector for each token ID.
  2. RMSNorm: adjust each row’s scale before the attention branch reads it.
  3. Q/K/V projections: create different representations for matching and contributing information.
  4. Attention: use Q/K scores to combine allowed V vectors, then project back to residual width.
  5. First addition: add that attention update to the branch’s original input.
  6. MLP and second addition: transform the normalized, updated representation and add another update.
  7. Next layer: receive the resulting sum and repeat with different learned weights.

Grounding: common.py loads the saved weights; step1b_layer0.py performs the forward computation. The training explanation describes the general mechanism behind learned weights, not training performed or inspected in this repository.

07 / Projection dimensions

Where did the additional 1,024 query features come from?

Reader questionHow can a 1,024-dimensional token representation produce a 2,048-dimensional query vector?

The input has 1,024 features per token. The query projection calculates 2,048 new features from those 1,024 inputs. A linear transformation can change a vector’s width; its weight matrix determines the output size.

q = normed @ w[p + "self_attn.q_proj.weight"].T
# [20, 1024] @ [1024, 2048] → [20, 2048]

It does not preserve the first 1,024 entries and append another 1,024. Each of the 2,048 output features is a learned weighted sum of the input features. All output features are computed by the projection.

A two-to-three-feature example

For an invented input [a, b], a projection could calculate:

output₀ = a + b
output₁ = 2a − b
output₂ = a + 3b

[2, 3] → [5, 1, 11]

Three output numbers can be derived from two inputs. This does not introduce an independent source of information; it expresses the same input through different combinations. In the actual model, training determines the combinations.

Expansion does not break the residual addition. Attention eventually concatenates its 16 head outputs into width 2,048. The output projection maps that back to 1,024, so residual + attn_out adds two matrices of shape [20, 1024].

Code: step1b_layer0.py, lines 69, 73, and 91–94. Weight shapes: config-walkthrough.md, “One layer’s tensors.”

08 / Reading the notation

What does Wq.T mean?

Reader questionWhat does the notation WQT mean in the query projection?

W denotes a weight matrix, q identifies the query projection, and .T means transpose: swap rows and columns. No new values are learned or calculated by transposing.

# Illustrative matrix, not actual model weights
W = [1  2  3]       W.T = [1  4]
    [4  5  6]             [2  5]
                         [3  6]

# Shape [2, 3] becomes [3, 2]

The model stores Wq as [2048, 1024]: output features first, input features second. Each row contains the 1,024 weights for one output query feature. Our input has token vectors arranged as rows, so we transpose the weights to align them for multiplication.

For token i and query feature j, the operation is:

q[i, j] = Σₖ normed[i, k] × Wq[j, k]
k runs from 0 to 1023

Read this as: multiply each input feature by its weight for output feature j, then add the 1,024 products. The same weight matrix is used at every token position.

Code: line 69. Wq is our explanatory shorthand for w[p + "self_attn.q_proj.weight"], not a separate variable in the file.

09 / Head partitioning

Are the 16 head groups sequential or random?

Reader questionAre the 2,048 projected query features partitioned sequentially across 16 heads, or assigned randomly? Can a feature appear in more than one head?

The division is sequential and fixed. Each projected query feature goes into exactly one head. No projected feature is duplicated or omitted by the reshape.

q = q.view(seq, NH, HD).transpose(0, 1)
# [20, 2048] → [20, 16, 128] → [16, 20, 128]

Projected features belong to one head. Input features can influence many.

The reshape partitions the 2,048 outputs of the query projection. It does not partition the original 1,024 input features into disjoint chunks.

Every output query feature can depend on all 1,024 input features. Head 0 uses rows 0–127 of Wq, head 1 uses rows 128–255, and so on. Each of those blocks still has 1,024 input columns.

All 1,024 inputs → Wq rows 0–127 → Head 0
All 1,024 inputs → Wq rows 128–255 → Head 1
…
All 1,024 inputs → Wq rows 1920–2047 → Head 15

This resolves the apparent overlap: one original input feature can influence many heads through different learned weights. One projected query feature occupies exactly one head. Head boundaries are fixed by the reshape; training learns what is encoded within those boundaries.

Every head still has all 20 token positions

We split features, not tokens. After the transpose, each of the 16 query heads contains 20 query vectors of width 128. Each head can form its own attention distribution over the permitted positions. Head roles are learned rather than predefined as “grammar,” “facts,” or other named tasks.

TensorAfter projectionAfter splitting and transposing
Q[20, 2048][16, 20, 128]
K[20, 1024][8, 20, 128]
V[20, 1024][8, 20, 128]

The later repeat_interleave operation shares KV heads across query heads. That is a separate step from this reshape; it does not randomly assign query features to heads.

10 / Preparing the matching space

Q and K get their own per-head RMSNorm

After the projections are reshaped, Q and K are normalized again. This is different from the first RMSNorm: the first one operates on each 1,024-feature residual row, while these norms operate on each 128-feature head vector.

q = rmsnorm(q, w[p + "self_attn.q_norm.weight"])
k = rmsnorm(k, w[p + "self_attn.k_norm.weight"])
# q: [16, 20, 128] · k: [8, 20, 128]

Keeping the shape matters: attention will compare one 128-feature query vector with one 128-feature key vector. Normalizing the entire 2,048-feature Q row would mix the heads, which is not what this code does.

Two RMSNorm scales, two jobs: input RMSNorm controls each residual-stream row before projection. Q/K RMSNorm controls each head’s matching vector after projection. V is not normalized by this Q/K-specific step.

Code: lines 77–78. The reduction behavior comes from rmsnorm at lines 30–36; the tensor shapes are documented in config-walkthrough.md.

11 / Adding position

RoPE rotates Q and K so distance affects matching

Attention sees vectors, but a language model also needs token order. Rotary positional encoding (RoPE) applies a position-dependent rotation to Q and K before their dot products. The same position-dependent rule is applied to both, so their comparison carries relative-position information.

cos, sin = rope_cache(seq, HD, THETA, dev, q.dtype)
q = apply_rope(q, cos, sin)
k = apply_rope(k, cos, sin)
rotated(x, position) = x ⊙ cos(position) + rotate_half(x) ⊙ sin(position)

rotate_half pairs the first 64 features with the second 64 features in this 128-wide head. RoPE changes the vector’s orientation according to position; it does not append extra features or change the tensor shape. It is applied to Q and K, not V.

Code: rope_cache and apply_rope at lines 39–47, then lines 80–81. The configured base is documented in config-walkthrough.md.

12 / Sharing keys and values

Grouped-query attention gives two query heads one KV head

Qwen3-0.6B has 16 query heads but only 8 key/value heads. The code repeats each K and V head twice so the score calculation can pair 16 query heads with 16 matching KV heads.

k = k.repeat_interleave(NH // NKV, dim=0)
v = v.repeat_interleave(NH // NKV, dim=0)
# [8, 20, 128] → [16, 20, 128]
Q₀, Q₁ → KV₀
Q₂, Q₃ → KV₁
…
Q₁₄, Q₁₅ → KV₇

This is a shape-and-sharing operation, not a new learned projection. It reduces the number of distinct K/V heads while retaining 16 query heads, saving KV-cache capacity compared with storing 16 K/V heads.

Code: lines 83–85. The mapping follows repeat_interleave order and NH // NKV = 2.

13 / Deciding who can contribute

Causal masking turns scores into a prefix-only weighted sum

The score matrix has one row for each query position and one column for each key position. In a decoder-only language model, position i may use positions up to i, but not future positions. The upper triangle is set to negative infinity before softmax.

scores = (q.float() @ k.float().transpose(-1, -2)) / (HD**0.5)
mask = torch.full((seq, seq), float("-inf"), device=dev).triu(1)
probs = (scores + mask).softmax(-1).to(q.dtype)
attn = probs @ v
score[i, j] = dot(q[i], k[j]) / √128
weights[i, :] = softmax(masked scores[i, :])
head_output[i] = Σⱼ weights[i, j] × v[j]

For the 20-token prompt, the score and probability tensors are [16, 20, 20]. Each row’s allowed probabilities sum to 1; masked future positions receive zero probability. The weighted sum combines values, not keys.

Transposing and reshaping concatenates the 16 head outputs into [20, 2048]. The output projection then returns attention to residual width [20, 1024], which is what makes the first residual addition possible.

Code: lines 87–94. The scale factor is √HD, with HD = 128.

14 / The second update

The gated MLP transforms each position independently

After the attention update is added, the MLP takes the new hidden matrix one row at a time. It expands each 1,024-feature row to 3,072 features along two learned branches, gates one branch with SiLU, multiplies them elementwise, and projects back to 1,024.

normed2 = rmsnorm(hidden, w[p + "post_attention_layernorm.weight"])
gate = normed2 @ w[p + "mlp.gate_proj.weight"].T
up = normed2 @ w[p + "mlp.up_proj.weight"].T
mlp_out = (F.silu(gate) * up) @ w[p + "mlp.down_proj.weight"].T
hidden = residual2 + mlp_out
[20, 1024] → gate, up: [20, 3072]
mlp_out = down_proj(SiLU(gate) ⊙ up): [20, 1024]
layer output = attention-updated hidden + mlp_out

Unlike attention, this MLP does not compare one token position with another. The same weights are applied independently to every row. It still changes the whole representation because each output feature can combine all 1,024 input features.

Complete layer 0: attention mixes information across allowed positions, the first residual addition preserves the incoming stream while adding that update, the MLP processes each position independently, and the second residual addition returns the final width-1,024 representation to the layer stack.

Answers

  1. Equal initially; not necessarily after attention. Identical IDs select the same embedding row, but position and available context can differ. Assuming they remain equal confuses a lookup with a contextual representation.
  2. The MLP receives the normalized original layer input, and can still produce a nonzero update. Only the attention addition is an identity in this case. Treating the whole layer as unchanged overlooks its second sublayer.
  3. It receives the current representation x₂. Earlier contributions are present in the accumulated sum, not supplied as separate history. A residual path does not create a recoverable update log.
  4. Scales: [20, 1]. Learned weights: [1024]. Scales depend on each input row; feature weights are shared across positions. One scale for the whole prompt would mix up the reduction axis.
  5. Values. Queries and keys determine the attention weights. Averaging the keys would confuse the matching representation with the information being passed onward.
  6. No. This script loads fixed, trained weights. Inputs change the Q/K/V activations; training is what changes their projection matrices. Confusing the two mixes inference with learning.
  7. The matrix multiplication. Transposing aligns the weight axes; reshaping groups existing outputs. Neither creates the query activations.
  8. Head 1, local feature 2, using zero-based indices. Original input feature 130 can influence every head through learned projection weights. Confusing input and projected feature indices misses the transformation between them.
  9. All 20 positions, each with 128 features. The reshape partitions features, not token positions.
  10. The final 128-feature axis. Q has shape [16, 20, 128] and K [8, 20, 128]; reducing the full projected row would combine features from separate heads. Confusing the residual norm with the per-head norm loses the reason for the second normalization.
  11. Its orientation changes according to position, but its width stays 128. RoPE combines the vector with its rotate-half version using position-specific sine and cosine values. It is not a concatenation of extra position features.
  12. Q6 and Q7. Zero-based KV head 3 is repeated into the consecutive pair of query-head slots 6 and 7. Treating the sharing as random would misread repeat_interleave.
  13. Keys 0 through 5. Position 5 may attend to itself and its prefix; future positions 6 onward are masked to negative infinity and receive zero probability after softmax. Confusing row and column indices reverses the causal direction.
  14. No. The MLP is position-wise: every row is processed independently. Its gate and up branches are [20, 3072], and the down projection returns [20, 1024] before the second residual addition. Calling it a cross-token mixer confuses it with attention.
